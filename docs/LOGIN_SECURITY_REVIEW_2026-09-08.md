# 로그인 보안 분석 — 2026-09-08

## 범위와 판정 기준

분석 대상은 현재 작업 트리의 데스크톱 로그인·가입·자격증명 저장 코드, 웹 비밀번호 재설정 요청/확정/큐, 관련 Supabase 마이그레이션, 서버 AI API 인증 연계다. 다른 작업의 미커밋 변경이 존재하므로 특정 커밋이나 배포본에 대한 인증 결과가 아니다. 애플리케이션 코드는 변경하지 않았다.

실제 `/user/login/god`, `/user/register/request`, `/user/password-reset/*` 구현은 외부 인증 서버에 있으며 이 저장소에 없다. 서버 DB의 비밀번호 해시, 세션 발급/폐기, MFA, 배포된 WAF와 제한값은 확인하지 못했다. 운영 계정 대상 로그인·메일 발송·무차별 대입은 수행하지 않았다. 아래 테스트 중 실행하지 않은 항목은 격리된 스테이징과 합성 계정에서 수행할 검증 계획이다.

판정은 **확인**(코드 또는 로컬 재현), **조건부**(설정이나 외부 서버 구현에 따라 영향 발생), **미확인**으로 구분한다. 클라이언트에 제한 코드가 없다는 이유만으로 서버에 제한이 없다고 판정하지 않는다.

## 확인된 문제와 수정안

### F1. 암호화 접두사로 시작하는 비밀번호가 그대로 저장됨 — 중간, 확인

- 근거: `src/secure_storage.py:121`은 입력이 `dpapi:` 또는 `fernet:`으로 시작하면 그대로 반환한다. `src/auth_client.py:2328`은 사용자가 입력한 원본 비밀번호를 저장 대상으로 넘기고, `:384`에서 이 함수를 호출한다.
- 시나리오: 사용자가 `dpapi:Example123!` 같은 유효한 비밀번호를 저장한다. 암호문으로 오인되어 JSON의 저장 비밀번호 필드에 원문이 기록된다. 자격증명 파일이나 백업을 읽을 수 있는 공격자는 복호화 없이 비밀번호를 얻는다. 재로딩 시 복호화에도 실패한다. 파일 접근 권한 없이 가능한 원격 탈취로 확인된 것은 아니다.
- 재현: 위 접두사의 합성 비밀번호 두 개 모두 `protect_secret(input) == input`이 참이었다. 실제 사용자 비밀번호는 사용하지 않았다.
- 수정: 일반 입력 API는 항상 암호화한다. 기존 암호문 마이그레이션은 별도의 명시적 API/타입으로 분리한다. 접두사만으로 암호화 여부를 판단하지 않는다. 영향받은 저장값을 제거하고 재입력을 받는다.
- 회귀 테스트: 두 접두사의 비밀번호를 임시 자격증명 파일에 저장한 뒤 원문이 파일에 없고 복호화 결과는 원문과 일치하는지 검사한다. 정상 비밀번호, 유니코드, 빈 값, 잘못된 암호문, 암호화 백엔드 실패도 검사한다.

### F2. 실패한 CAPTCHA가 피해자의 재설정 한도를 소진 — 중간, 확인

- 근거: `api/_lib/password-reset-proxy.mjs:124`에서 IP와 identifier 카운터를 먼저 증가시키고 `:137`에서 CAPTCHA를 검사한다. 기본 identifier 한도는 10분당 3회다 (`password-reset-rate-limit.mjs:3`).
- 시나리오: 공격자가 피해자 identifier로 CAPTCHA 없는 요청을 3회 보낸다. 이후 피해자가 올바른 CAPTCHA로 요청해도 큐에 들어가지 않는다. 모든 응답이 202라서 피해자는 메일이 올 것으로 생각한다. 새 시간 구간마다 반복하면 해당 identifier의 복구를 계속 방해할 수 있다. 기존에 발급된 링크나 다른 복구 수단까지 무효화되는 것은 아니다.
- 로컬 재현: 실패 요청 3회 후 유효 요청의 응답은 202, 큐 등록은 0건이었다.
- 수정: 저비용 IP/네트워크 제한 → CAPTCHA 검증 → 계정별 실제 발송 한도 순으로 분리한다. IP 제한은 CAPTCHA 실패에도 적용하지만 계정별 발송 한도는 실패한 CAPTCHA로 차감하지 않는다. 분산 공격에는 추가 위험 평가와 별도 복구 경로를 둔다.
- 회귀 테스트: 실패 CAPTCHA 3회 뒤 정상 요청은 큐에 1회 등록되어야 한다. 정상 검증 요청의 발송 한도, 다중 인스턴스 동시성, 저장소 장애 시 차단은 유지되어야 한다.

### F3. CAPTCHA 설정과 프런트엔드가 연결되지 않음 — 중간, 조건부 장애/방어 공백

- 근거: `public/password-reset.js:49`는 identifier와 program_type만 전송한다. 서버는 `password-reset-proxy.mjs:138`에서 captcha_token을 읽는다. `password-reset-rate-limit.mjs:390`은 비밀키가 없으면 허용하고, `:392`는 비밀키가 있지만 응답 토큰이 없으면 거절한다. 현재 HTML에 위젯이 없고 `vercel.json` CSP도 Turnstile 외부 스크립트/프레임을 허용하지 않는다.
- 시나리오: 비밀키를 설정하면 정상 웹 요청이 모두 202로 보이지만 메일은 발송되지 않는다. 비밀키가 없으면 CAPTCHA는 수행되지 않는다. 후자의 경우에도 기존 rate limit은 작동하므로 전체 방어가 사라지는 것은 아니다.
- 수정: 클라이언트 위젯, 응답 토큰 전달, 최소 CSP 허용 목록, 서버 검증을 함께 배포한다. CAPTCHA 필수 모드에서는 누락 설정을 준비 상태 검사에서 검출한다. 검증 응답의 예상 hostname/action도 확인한다.
- 회귀 테스트: 실제 브라우저와 스테이징 키로 정상 토큰 발송 성공, 누락/만료/재사용/다른 action·hostname 거절, CSP 오류 없음, 설정 누락 탐지를 확인한다. 단위 테스트에서 CAPTCHA를 항상 참으로 대체하는 것만으로 완료하지 않는다.

### F4. 재설정 확정 경로에 자체 요청 제한 없음 — 중간, 중계 계층 확인/서버 영향 미확인

- 근거: `password-reset-proxy.mjs:116` 내부에만 limiter 호출이 있고 confirm은 `:174`에서 곧바로 외부 서버에 전달된다. IP도 전달하지 않는다.
- 시나리오: 공격자가 형식만 맞는 임의 토큰으로 확정 요청을 반복한다. 각 요청이 외부 검증 서버까지 도달해 자원을 사용한다. 서버의 실제 토큰 엔트로피·만료·제한이 미확인이므로 토큰 추측 성공이나 비밀번호 변경 우회까지 입증한 것은 아니다.
- 로컬 재현: 임의 토큰 요청 12회에서 중계 limiter 호출 0회, 가짜 upstream 호출 12회였다.
- 수정: 확정 경로에도 IP/네트워크와 전역 제한을 추가한다. 토큰 단위 제한만으로는 임의 토큰 교체 공격을 막을 수 없다. 외부 서버의 직접 접근 경로도 동일하게 보호한다. 비밀 토큰은 로그나 제한 키에 원문으로 저장하지 않는다.
- 회귀 테스트: 제한 N까지 전달되고 N+1부터 중계에서 차단되는지, 임의 토큰 교체/다중 인스턴스/동시 요청/시간 경계/저장소 장애를 검사한다. upstream 직접 경로도 별도로 검사한다.

### F5. 아이디 존재 여부를 알려주는 공개 계약 — 중간, 코드상 정보 노출 설계 확인

- 근거: `src/auth_client.py:1681`은 인증 없이 `/user/check-username/{username}`을 호출하고 available 값을 반환한다. `src/login_window.py:1038`은 결과를 화면에 표시한다. 실제 운영 응답은 호출하지 않았다. available=false가 예약명 등도 포함할 수 있으므로 모든 응답이 실제 계정 존재를 확정하는 것은 아니다.
- 시나리오: 공격자가 아이디 후보를 조회해 가입 불가 후보를 좁힌 후 stuffing/spraying 대상을 선별한다. 재설정 API의 공통 문구만으로 이 별도 노출을 해결할 수 없다.
- 수정: 비공개 로그인 식별자라면 공개 중복 조회를 없애고 소유권 확인 이후 가입 처리로 전환한다. 공개 사용자명 중복확인이 필요한 제품이라면 정보 노출을 명시적으로 수용하고 제한·CAPTCHA·대량 탐지로 자동 수집 비용을 높인다. UI 문구만 숨겨서는 API 노출이 없어지지 않는다.
- 회귀 테스트: 존재/부재/예약/비활성 계정의 로그인·가입·중복조회·복구 응답 코드, 본문, 길이, 시간 분포를 비교한다. 공통 응답 정책과 실제 호출 한도를 검증한다.

### F6. Remember Me가 원본 비밀번호를 복원 가능한 형태로 장기 보관 — 중간, 설계 위험 확인

- 근거: `src/auth_client.py:2316`의 저장 함수와 `:1933`의 세션 정리. 로그아웃 시 token/user_id를 제거하지만 저장 비밀번호는 유지한다.
- 시나리오: 같은 OS 사용자 권한의 악성 프로세스는 앱이 복원 가능한 비밀번호에 접근할 수 있다. 로그아웃 후에도 저장 비밀번호가 남는다. DPAPI/ACL은 유효한 방어지만 같은 사용자 권한의 실행을 격리하지 않는다. 보관 파일을 읽는 것만으로 일반 DPAPI 암호문이 복호화된다고 주장하지 않는다.
- 수정: 원본 비밀번호 저장을 없애고 기기별 취소 가능한 랜덤 refresh token으로 전환한다. 서버에는 토큰 해시만 저장하고 회전·재사용 감지·만료·기기 철회를 구현한다. 로그아웃에서 자동 로그인 해제와 서버 폐기를 일관되게 처리한다.
- 회귀 테스트: 디스크에 원본 비밀번호가 저장되지 않는지, 회전 후 이전 토큰 재사용 차단, 로그아웃/비밀번호 변경/기기 철회 후 갱신 차단, Remember Me 해제 후 재시작 시 로그인 요구를 확인한다.

### 비밀번호 SHA-256 전처리의 별도 주의점

`src/auth_client.py:471`은 비밀번호를 SHA-256으로 변환해 전송한다. 이 값은 로그인에 재사용 가능한 비밀번호 상당의 비밀이다. 이것만으로 재전송 공격이나 credential stuffing을 막지 못한다. 주석은 서버의 adaptive hash 저장을 주장하지만 서버 코드는 없으므로 실제 알고리즘·salt·비용은 미검증이다.

또한 가입 서버에 원본 대신 digest만 전달하면 원본의 길이·유출 비밀번호 여부를 그 digest만으로 완전히 검증할 수 없다. 정책 시행을 클라이언트 검사에 맡기지 않도록 가입/변경 계약을 재설계해야 한다. 이행 시 기존 계정 호환성과 이중 해싱을 검증하고, TLS를 유지하며, 서버 저장은 Argon2id 등 적절한 비밀번호 해시를 사용한다. digest를 일반 로그·진단 정보에 기록하지 않는다.

### IP와 제한 키의 추가 검증 사항

재설정 중계는 X-Forwarded-For의 첫 주소를 사용한다 (`password-reset-proxy.mjs:105`). 실제 호스팅 프록시가 이 헤더를 덮어쓰는지는 코드만으로 판정할 수 없으므로 헤더 위조 가능성을 확정 취약점으로 적지 않았다. IPv6 정규화는 있지만 네트워크 대역 집계는 없으며 identifier도 정규화된 입력 문자열 단위이므로 아이디/이메일 별칭이 동일 계정을 가리키는 경우 서버에서 계정 기준 합산이 필요하다. 고정 시간 구간은 경계 양쪽에 요청이 몰릴 수 있어 목표 정책이 rolling window라면 구현을 변경해야 한다.

## 수정 우선순위

1. F1 암호화 접두사 처리와 F2 계정 한도 차감 순서를 수정한다.
2. F3 CAPTCHA 전체 흐름을 연결하고 F4 확정 경로 제한을 추가한다.
3. 외부 인증 서버 코드/설정에서 로그인 제한, force 처리, 토큰-주체 결합, reset 일회성, 세션 철회를 검증한다. 이 검증 전 원격 계정 탈취 방어에 대한 최종 합격 판정은 보류한다.
4. F5 식별자 노출 정책을 결정하고, F6 원본 비밀번호 보관을 기기별 토큰으로 대체한다. 서버 비밀번호 정책과 MFA를 일관되게 적용한다.
