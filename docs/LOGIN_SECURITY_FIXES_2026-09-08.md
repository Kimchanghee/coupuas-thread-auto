## 공격 시나리오, 수정, 회귀 검증

| 항목 | 공격 시나리오와 대응 | 검증 방법 |
|---|---|---|
| Brute Force | 한 계정에 반복 추측. DB 원자적 계정·IP·네트워크·전역 제한 적용 | 병렬 요청에서도 허용 횟수 초과하지 않음 |
| Credential Stuffing | 재사용된 자격 증명으로 로그인. 유출 비밀번호 신규 설정 차단, 등록된 MFA 강제 | 유출 목록 응답 거부, 비밀번호만으로 MFA 계정 로그인 실패 |
| Password Spraying | 여러 계정에 소수 비밀번호 시도. 계정 외 IP·네트워크·전역 제한 | 여러 계정 시도 시 공유 제한, 차단 IP가 후속 버킷을 소진하지 않음 |
| 계정 열거 | 가입·아이디 확인·로그인 응답 차이 비교. 공개 응답 통일 및 동일 비밀번호 검증 작업 | 존재/미존재 응답 및 bcrypt 호출 횟수 비교. 실환경 통계적 타이밍 검증은 별도 필요 |
| 로그인 우회 | 강제 로그인 또는 오래된 인증 상태 이용. 사용자 잠금 아래 비밀번호·MFA 재검증 | 잘못된 비밀번호+force 거부, MFA 없이 세션 미발급 |
| 재설정 우회 | 세션으로 복구 이메일 변경, 토큰 재사용, 요청 남용. 이메일 변경 차단, 단일 사용 토큰 유지, CAPTCHA/제한 강화 | 이메일 변경 403, 재사용 거부, 실패 CAPTCHA가 피해 계정 발송 한도 미소진 |
| 세션 탈취 | 탈취 세션으로 복구 수단 변경·장기 인증 확보. 민감 작업 비밀번호 재확인, 세션/장기 토큰 폐기 | 재설정 후 이전 세션/장기 토큰 거부, MFA 변경 후 다른 세션 폐기 |
| 세션 고정 | 이전 세션/갱신 토큰 재사용. 새 세션 발급과 이전 세션 비활성화 | 회전 후 이전 세션 거부, 동시성 관련 현재 읽기 잠금 적용 |
| Remember Me | 로컬 저장 비밀번호 탈취. 비밀번호 저장 제거, OS 보호된 회전 토큰으로 대체 | 기존 저장 비밀번호 제거, 회전·재사용 탐지·만료 JWT 로그아웃 폐기 |
| 비밀번호 정책 | 짧거나 유출된 비밀번호, bcrypt 길이 예외. 신규 15~128자, 유출 검사, 길이 예외 처리 | 길이/반복 패턴/유출 거부, 긴 기존 입력에서 서버 오류 없음 |
| MFA | 비밀번호만으로 우회, 코드 재사용, 무단 해제. 암호화 TOTP·일회 복구 코드·재인증 | 등록/로그인/해제, 코드 재사용 거부, 비밀 암호화와 복구 코드 해시 저장 |
| 로그인 Rate Limit | 병렬 요청 및 XFF 위조. 공유 DB 원자적 제한, 신뢰 프록시 경계 검증 | 병렬 SQLite 테스트, 위조/잘못된 XFF 및 신뢰 경계 테스트 |

MFA는 사용자가 등록하면 서버에서 강제된다. 모든 기존 사용자에게 강제 등록하는 정책은 포함하지 않는다. 탈취된 현재 유효 토큰의 사용 자체를 전부 막는다고 보장하지 않는다. 등록/아이디 확인 응답 변경은 stmaker 경로 중심이며 다른 제품 인증 전반을 감사한 것은 아니다.

## 운영 적용 순서

1. 운영과 같은 DB의 격리 환경에서 백업 및 아래 동시성 검증을 실시한다. DB 런타임 계정이 테이블 생성/권한 설정에 필요한 권한을 가져야 한다.
2. 인증 서버에 `AUTH_MFA_ENCRYPTION_KEY`를 안전하게 생성한 Fernet 키로 설정한다. 키를 저장소/로그에 남기지 않고 영속 보관한다. 키 분실은 등록된 인증 앱의 검증 실패를 초래한다.
3. `TRUSTED_PROXIES`를 실제 역방향 프록시 주소/CIDR로만 설정한다. Vercel에서는 기존 플랫폼 신뢰 헤더 검증을 유지한다. Vercel 밖에서는 실제 프록시 주소만 설정한다.
4. 사이트에 `TURNSTILE_SECRET_KEY`, `TURNSTILE_SITE_KEY`, `TURNSTILE_EXPECTED_HOSTNAMES`(쉼표 구분)를 설정한다. 위젯 action은 `password_reset`이다. 기존 재설정 토큰/공유 제한 저장소 설정도 유지한다. 설정 누락 시 복구 요청은 안전하게 실패한다.
5. 인증 서버와 새 클라이언트/사이트를 조율하여 배포한다. 서버 우선 적용 시 구버전 stmaker 가입은 업데이트를 요구하게 된다. 기존 비밀번호 로그인은 호환된다. 자동 로그인 저장 정보는 새 토큰 방식으로 다시 설정한다.
6. 테스트 계정으로 가입→MFA 등록→로그인→자동 로그인→로그아웃→재설정→이전 토큰 거부까지 실제 환경에서 확인한다. 복구 코드는 한 번만 표시하므로 사용자가 별도 보관한다.

서버는 신규 `account_security`, `remember_tokens` 테이블을 초기화하고 PostgreSQL에서 해당 보안 테이블의 RLS/공개 역할 권한을 제한한다. 기존 제한 테이블도 보호한다. 현재 회귀 테스트의 DB 동시성은 SQLite에서 검증했다. PostgreSQL/MySQL 운영 버전에서 로그인/갱신/재설정/폐기를 교차 실행하여 대기 중 생성된 세션까지 폐기되는지 추가 검증해야 한다.

신규 가입과 재설정은 HIBP Pwned Passwords 범위 API를 사용한다. 비밀번호 원문 대신 SHA-1 접두사만 전달하며 장애/잘못된 응답은 503으로 차단한다. 외부 HTTPS 연결과 장애 처리를 점검한다. https://haveibeenpwned.com/API/v3#PwnedPasswords

복구 이메일 변경은 현재 차단했다. 향후 변경 기능은 기존/신규 이메일 검증과 재인증을 갖춘 별도 흐름으로 구현해야 한다. MFA 등록 이후 구버전 인증 서버로 단순 롤백하면 MFA 보호가 사라지므로 조율된 롤백이 필요하다.

## 검증 범위

- 백엔드 전체 테스트: 89 passed (기존 라이브러리 deprecation 경고 4건).
- 클라이언트 전체 테스트: 465 passed (인증 관련 106개 포함).
- 사이트 Node 테스트: 71 passed.
- 한국어 로그인/MFA 설정 화면을 오프스크린 렌더링하여 확인.
- 독립 보안 검토 후 MySQL snapshot read에서 세션 폐기가 누락될 수 있는 조회에 현재 읽기 잠금 추가.
- 운영 계정 공격, 운영 환경 변수 변경, 운영 배포는 실행하지 않았다. 코드 푸시만으로 운영 보호 적용이 완료되는 것은 아니다.
